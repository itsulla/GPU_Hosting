Step 6

Choose Your Quantization Format

Your format choice dictates which inference engine you can use.

GGUF

LOCAL / HYBRID

GGUF is central to llama.cpp and Ollama workflows and can support CPU/GPU offload. Current vLLM releases also support GGUF, but document it as under-optimized and without tensor parallelism.

Enginesllama.cpp, Ollama, vLLM*
HardwareCPU / GPU hybrid
Trade-offRuntime support varies

EXL2

VARIABLE-BIT

Variable bits-per-weight per layer. Allocates more bits to sensitive attention layers, fewer to tolerant feed-forward layers.

  • Engines: ExLlamaV2
  • Hardware: Pure GPU only
  • Trade-off: Runtime-specific; test model support

AWQ

GPU-NATIVE

Activation-aware weight quantization. Common in GPU serving stacks, with model, kernel, and hardware-specific behavior.

  • Engines: vLLM, HF TGI
  • Hardware: Pure GPU only
  • Trade-off: Can be slower than unquantized weights

GPTQ

ESTABLISHED

Post-training weight quantization with broad historical support. Current kernels and loading paths differ by serving stack.

  • Engines: vLLM, TGI, AutoGPTQ
  • Hardware: Pure GPU only
  • Trade-off: Kernel and model compatibility varies

FP8

HOPPER / BLACKWELL

Eight-bit floating point paths can reduce weight memory on supported hardware and runtimes. Quality, calibration requirements, kernel support, and speed are model- and implementation-specific.

EnginesvLLM, TensorRT-LLM, SGLang
HardwareH100 / H200 / B200 / RTX 5090
MemoryNominally ~50% of FP16 weights
CalibrationMethod-dependent
Trade-offEvaluate exact model + backend
Compatibility warning: quantization can change quality, fit, cold-start time, and throughput. Verify the exact model revision, format, runtime version, GPU backend, context, and representative tasks before deployment.
Step 7

Choose Your Inference Engine

Choose by model and format support, concurrency, topology, operating environment, API behavior, and security—not a one-line winner label.

vLLM — High-Throughput Serving

Serving-focused runtime with continuous batching, prefix caching, distributed operation, and OpenAI-compatible routes. Benchmark the exact workload.

  • Concurrency: Workload-dependent
  • Formats: AWQ, GPTQ, FP8, GGUF*
  • Setup: Medium (Docker)
  • GGUF: Under-optimized; no tensor parallelism
  • API: OpenAI-compatible routes
  • Best fit: Concurrent GPU API serving

Ollama — Local-First Model Runner

Simple model lifecycle and local HTTP APIs across common desktop and server platforms.

  • Concurrency: Benchmark your context and parallelism
  • Formats: GGUF and supported imports
  • Setup: Easy
  • Platforms: Linux / macOS / Windows
  • API: Native + OpenAI-compatible subset
  • Best fit: Local and single-node workflows

Hugging Face TGI — Docker-First Serving

Hugging Face serving stack with batching, streaming, telemetry, and several quantization paths. Verify current architecture support and release freshness.

  • Concurrency: Workload-dependent
  • Formats: AWQ, GPTQ, BnB, FP8 paths
  • Setup: Docker-focused
  • API: Messages API compatibility
  • Advantage: Hugging Face ecosystem integration
  • Best fit: Supported HF models and pipelines

llama.cpp — Local, Edge & Hybrid

CPU/GPU inference and a built-in server centered on GGUF, broad hardware reach, and configurable parallel decoding.

  • Concurrency: Hardware and configuration-dependent
  • Formats: GGUF and k-quants
  • Setup: Easy to medium
  • Advantage: Broad local hardware support
  • API: Built-in compatible server
  • Best fit: Local, edge, and CPU-offload workloads

SGLang — Advanced GPU Serving

Serving stack with RadixAttention, continuous batching, structured outputs, and distributed parallelism. Benchmark the exact model and GPU.

  • Concurrency: Workload-dependent
  • Formats: FP8, AWQ, GPTQ paths
  • Setup: Medium (Docker/pip)
  • Hardware: Backend/version-specific
  • API: OpenAI-compatible routes
  • Best fit: Structured and distributed serving

Option B: Private vLLM + Docker

Loopback bind, pinned image, API key, private proxy

HARDENED START
Security boundary: keep vLLM on loopback or a private network. Its API key does not protect every developer endpoint; add an authenticating TLS reverse proxy and firewall before remote access.
# vLLM v0.26.0 with Docker (requires NVIDIA Container Toolkit) # Capacity assumption: 2x H200 141GB or equivalent. 2x 80GB GPUs are below the 168GB planning estimate. VLLM_API_KEY=$(openssl rand -hex 32) export VLLM_API_KEY docker run --runtime nvidia --gpus all \ -v ~/.cache/huggingface:/root/.cache/huggingface \ -p 127.0.0.1:8000:8000 --ipc=host \ vllm/vllm-openai:v0.26.0 \ --model meta-llama/Llama-3.1-70B-Instruct \ --max-model-len 8192 \ --tensor-parallel-size 2 \ --api-key "$VLLM_API_KEY" # Test the private endpoint. Do not publish port 8000 directly. curl http://localhost:8000/v1/chat/completions \ -H "Authorization: Bearer $VLLM_API_KEY" \ -H "Content-Type: application/json" \ -d '{"model":"meta-llama/Llama-3.1-70B-Instruct","messages":[{"role":"user","content":"Hello!"}],"max_tokens":256}'
