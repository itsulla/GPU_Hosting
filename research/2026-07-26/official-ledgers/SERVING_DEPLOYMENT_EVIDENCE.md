## Quantization facts and caveats

- **GGUF is a model file/container ecosystem associated with llama.cpp**, with conversion and architecture-registration steps documented in the official [HOWTO](https://github.com/ggml-org/llama.cpp/blob/master/docs/development/HOWTO-add-model.md). A “GGUF supported” checkbox does not mean every architecture, tokenizer, multimodal projector, or quant type works in every runtime.
- **AWQ**: official [AutoAWQ repo](https://github.com/casper-hansen/AutoAWQ) describes 4-bit AWQ and reports a 2x inference-speedup claim in its README; latest release checked **v0.2.9 (2025-05-11)**. Repository/readme claims are not cross-runtime benchmarks. Check whether the project’s kernels and current Transformers/runtime integration are maintained for the target GPU.
- **GPTQ**: official [AutoGPTQ repo](https://github.com/AutoGPTQ/AutoGPTQ) describes GPTQ quantization; latest release checked **v0.7.1 (2024-03-01)**. Its age is an explicit caveat: do not imply the package is the best/current quantizer without checking the target serving stack’s native GPTQ path.
- **Runtime support is not interchangeability**: vLLM, SGLang, TGI, TensorRT-LLM and llama.cpp list overlapping names (AWQ/GPTQ/FP8/etc.) but use different kernels, model formats, hardware limits, and loading paths. Article should say “supported in [runtime/version] under documented conditions,” not “quantized model works everywhere.”
- Quantization can reduce VRAM and improve memory-bound throughput, but may reduce quality and can alter prompt/KV-cache behavior. Test task quality, long-context behavior, batch/concurrency, cold start, and OOM boundaries on the exact GPU/runtime.

## OpenAI-compatible serving, security and operations

- OpenAI compatibility is an API-shape convenience, not behavioral identity. Providers differ in supported routes, streaming, tool calls, structured outputs, embeddings, token accounting, error formats and model-name semantics. Test the exact SDK operations used by the app.
- **Authentication/TLS**: llama.cpp server flags explicitly expose API-key and PEM TLS options; for vLLM/TGI/SGLang/Ollama, use the current server flags/docs plus a reverse proxy or private network where needed. Never publish a raw inference port without an explicit auth/TLS/network design. Do not claim any stack is secure-by-default without testing a fresh deployment.
- **Observability**: TGI officially documents OpenTelemetry/Prometheus; llama.cpp documents optional Prometheus-compatible metrics. Cloud gateways (below) add request/token/cost analytics, logging, retries/fallbacks and rate limiting. For any stack, instrument queue time, prompt/output tokens, TTFT, generation rate, GPU utilization/VRAM, OOM/restarts, 4xx/5xx, and model-load/cold-start time.
- **Docker**: official Docker paths exist for Ollama and TGI; vLLM publishes official Docker deployment docs. GPU containers still require host drivers/runtime/toolkit, persistent model cache/storage, health checks, resource limits, secrets handling and an update/rollback plan.

## Rented-GPU / managed inference deployment evidence

- **Runpod Serverless**: [overview](https://docs.runpod.io/serverless/overview), [vLLM](https://docs.runpod.io/serverless/workers/vllm). Official docs say workers run a custom Docker container, start on demand and stop idle workers; cold starts queue requests until a worker is available. vLLM docs highlight paged attention, continuous batching and OpenAI compatibility. Implication: serverless GPU is operationally convenient but cold-start/queue behavior must be measured; preload/custom images can reduce model-download time.
- **Modal**: [official vLLM example](https://modal.com/docs/examples/vllm_inference). Example uses GPU selection, persistent HF/vLLM cache volumes, `scaledown_window`, startup timeout, port, and `target_concurrency`; its sample explicitly sets `unauthenticated=True` to make endpoint public. Implication: do not copy that sample’s public setting into production; add auth and validate concurrency/cost/cold starts.
- **Fly.io**: [GPU docs](https://fly.io/docs/gpus/), [private networking](https://fly.io/docs/networking/private-networking/). Official docs expose GPU Machines and private 6PN networking; Fly warns a Machine’s `FLY_PRIVATE_IP` is not static. Implication: private inference can be reached over Fly private networking, but service discovery must not assume a permanent private IP; use internal DNS/appropriate service identity.
- **Railway**: [Dockerfiles](https://docs.railway.com/builds/dockerfiles), [private networking](https://docs.railway.com/reference/private-networking), [deployments/healthchecks](https://docs.railway.com/deploy/deployments). Official docs support Dockerfile/image deployment, private networking and health checks/restart/scale concepts. GPU availability, region, instance type and pricing are plan/product-specific; verify live account options before writing “Railway GPU hosting” as universal.
- **Render**: [Docker deploys](https://render.com/docs/docker), [private services](https://render.com/docs/private-services). Official docs support Docker deploys, private services, health checks and operational monitoring. Treat Render as an app/private-service layer; confirm current observability page and GPU availability before suggesting it as a GPU inference host.
- **Cloudflare Workers AI**: [official overview](https://developers.cloudflare.com/workers-ai/). Cloudflare describes serverless GPU model execution on its global network and an OpenAI-compatible API endpoint; custom private models/higher limits are directed to a custom requirements process. Good managed option for supported models; not evidence that arbitrary self-hosted weights can be mounted there.
- **Cloudflare AI Gateway**: [overview](https://developers.cloudflare.com/ai-gateway/), [get started](https://developers.cloudflare.com/ai-gateway/get-started/). Current docs describe unified/OpenAI-compatible access, provider API-key pass-through or BYOK, analytics for requests/tokens/cost, logging, caching, rate limiting, retries and fallbacks. Use as an app-to-provider control plane; it does not turn a private GPU into a publicly reachable service without networking/auth configuration.

## AI-app deployment guidance

- **Vercel**: [AI SDK](https://sdk.vercel.ai/docs), [AI Gateway](https://vercel.com/docs/ai-gateway), [Function limits](https://vercel.com/docs/functions/limitations). Official pages position AI SDK/Gateway for multi-provider AI apps; Gateway advertises no token markup, spend monitoring, provider options/fallbacks/timeouts/caching and authentication/BYOK. Function docs state timeout yields `FUNCTION_INVOCATION_TIMEOUT`/504 and show plan/runtime-dependent maximums (the fetched current page reports 300s/5 min defaults/max for some Node/Python cases with fluid compute). Implication: Vercel is a strong frontend/API control plane, but long-running generation, model weights and GPU residency belong on a separate inference endpoint unless the workload fits function limits.
- **Netlify**: [Functions overview](https://docs.netlify.com/functions/overview/), [environment variables](https://docs.netlify.com/build/environment-variables/overview/). Official docs say Functions deploy with the site, auto-scale, expose logs/usage/metrics, and support AI SDK examples; environment variables support deploy contexts/scopes and secrets. Implication: keep inference credentials in server-side env vars, never browser code; use async/background patterns or a private endpoint for long generations.
- **Railway / Render / Fly**: use Dockerized app gateways or private services to connect the public app to inference over private networking where available. Add an application-level timeout, streaming handling, retry/idempotency policy, request size/token limits and a health endpoint; platform “deploy succeeded” is not proof the model is loaded or ready.
- **Private inference endpoint pattern**: app server holds the inference base URL and secret; client calls app server; app server authenticates and forwards to private endpoint; endpoint is restricted by private network/VPC/allowlist or authenticated gateway; stream response through without exposing provider credentials. Verify DNS, TLS certificate hostname, egress rules, CORS (ideally no direct browser access), auth failure behavior, timeouts, cancellation and retry duplication.

## Claims that should not be made without testing

1. Exact tokens/sec, latency, throughput, max context, concurrency or GPU count for any model/runtime combination.
2. “AWQ/GPTQ/GGUF works” without specifying runtime version, model revision, quant type, GPU/backend and route tested.
3. “OpenAI-compatible” means drop-in support for every OpenAI SDK feature.
4. Public deployment is authenticated, encrypted or private by default.
5. A Docker image is production-ready without checking drivers/toolkit, persistent cache, health/readiness, restart behavior and secrets.
6. Serverless GPU is cheaper/faster overall without measuring cold start, idle/sustained billing, queueing and model-download/storage behavior.
7. Railway/Render/Vercel/Netlify/Fly offer a particular GPU, region, plan, timeout or price without checking the live account/product page.
8. A model’s quantized quality is preserved; run representative evals and long-context/tool-use tests.
9. A health endpoint proves inference readiness; test an actual generation/embedding request and model-load state.
10. A private endpoint is safe merely because it is non-public DNS; verify network ACLs, TLS, authentication, logging/redaction and abuse/rate limits.
